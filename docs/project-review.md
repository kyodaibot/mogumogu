# Meal App 项目概述

本文件记录长期目标和共同约定，不代表所有功能都应立即实现。具体开发以对应阶段计划（plans/phase-N.md）和用户当前指令为准。

## 1. 项目目标

开发一个以日历为中心的饮食推荐应用。用户在日历中记录行程和实际吃过的食物，系统结合用户 Profile 推荐下一餐。

项目同时用于：
- 学习前端、后端、AI 应用和基础设施开发，建立便于组员共同开发的环境。
- 部署到 AWS，作为可实际访问的全栈作品，展示接口设计、数据管理、自动化检查、云部署和基础运维能力。

## 2. 核心用户流程

日常记录：
1. 注册或登录，首次填写 Profile。
2. 在日历中选择日期，新增、查看、修改或删除当天的行程和饮食记录。

获取推荐：
1. 在日历中选中目标日期（默认今天），点击右下角的饮食助手按钮，打开聊天面板。
2. 点击预设问题（如“10 月 28 日午餐吃什么？”）或自己输入问题。
3. 系统自动读取 Profile、相关行程和近期饮食记录，返回一句回复和三个备选方案（备选，不表示需要全部食用）。
4. 如对结果不满意，可继续输入（如“不想吃辣”“只有 15 分钟”“想在便利店买”），饮食助手据此更新三个方案。

通过预设问题获取推荐无需输入文字，也无需重复填写已保存的信息。

## 3. MVP 功能

### 3.1 账号与认证

- 注册、登录、退出、获取当前登录用户。
- 用户名与密码登录，密码使用 Argon2id 哈希保存。
- Go 后端签发 JWT，通过 HttpOnly Cookie 保存；校验签名、过期时间、签发者、受众及必要身份字段。
- 退出时清除 Cookie，并在 PostgreSQL 中记录撤销，使旧令牌失效。令牌过期后重新登录。
- 实现基本登录限流、CSRF 防护和适当的 Cookie 配置；生产环境使用 HTTPS。
- 用户数据按用户隔离。所有数据访问依据服务端验证后的身份授权，不信任客户端提交的 user_id。
- 账号等级（Normal、Pro，见 GLOSSARY.md 和 plans/archive/account-tiers.md）：新用户都是 Normal。等级只能由管理员在服务器上用 `cmd/admin` 修改，没有对应的 API 或管理页面。目前 Pro 只是每天的调用额度更多（3.6）；导航栏的用户名旁显示账号等级（「Normal」或「Pro」）。等级只在 Go 中判断，不传给 AI 服务。

### 3.2 Profile

支持读取、保存和修改：

| 字段 | 含义 | 类型 |
|---|---|---|
| height_cm | 身高，单位 cm | 数值 |
| weight_kg | 体重，单位 kg | 数值 |
| age | 年龄 | 整数 |
| has_exercise_habit | 是否有健身习惯 | 布尔值 |
| allergens | 过敏原列表 | 字符串数组或 null |
| goal | 目标 | 枚举：build_muscle（增肌）、lose_fat（减脂） |

allergens 的取值含义：
- null：尚未填写。
- []：用户确认无已知过敏原。
- 非空数组：已填写的过敏原。

### 3.3 日历主页面

日历是应用的主要入口。

- 查看并切换月份；默认选中今天，可选择其他日期。
- 在日期中展示行程和饮食记录的摘要；点击日期后展示当天详细记录。
- 在所选日期新增、修改、删除行程和饮食记录。
- 右下角的饮食助手按钮（只在日历页显示），以所选日期为目标日期提问（见 3.6）。

日历组件在阶段 2 选择，满足基本日期展示和点击交互即可。

### 3.4 行程记录

| 字段 | 含义 |
|---|---|
| title | 活动名称（如“上课”） |
| starts_at | 开始日期与时间 |
| ends_at | 结束日期与时间 |
| notes | 可选备注 |

- 同一天允许多条行程。支持新增、按日期范围查看、修改和删除。
- 结束时间必须晚于开始时间；允许跨午夜行程。
- 查询某天的行程时，返回与当天时间范围重叠的行程。
- 每条行程独立存储在 schedule_events 表。

### 3.5 饮食记录

记录用户吃过的食物，也允许记录未来日期的饮食。生成推荐时，饮食历史窗口不晚于今天，未来日期的记录不会被当作已食用（见 3.6）。

| 字段 | 含义 | 单位 |
|---|---|---|
| date | 饮食日期 | YYYY-MM-DD |
| meal_type | 早餐、午餐、晚餐或加餐 | — |
| content | 食物名称或描述 | — |
| calories | 热量 | kcal |
| protein_g | 蛋白质 | g |
| fat_g | 脂质 | g |
| carbs_g | 碳水化合物 | g |

- 同一天、同一餐次允许多条记录。支持新增、按日期或日期范围查看、修改和删除。
- 营养字段表示该条记录实际食用份量的总量，不是每 100 克的含量。
- 营养字段可留空：null 表示未知，0 表示用户明确填写为零；数值必须非负。
- 第一版由用户手动填写。

### 3.6 饮食助手

术语见仓库根目录 GLOSSARY.md（饮食助手、对话、对话历史、目标日期、轮、预设问题）。

聊天面板：
- 日历页右下角显示悬浮按钮，点击后打开聊天面板。桌面端为右下角的浮动面板，手机端全屏显示。只在日历页显示。
- 面板顶部显示当前目标日期，即日历上选中的日期。
- 对话开始前显示 4 个预设问题：「{日期}早餐吃什么？」「{日期}午餐吃什么？」「{日期}晚餐吃什么？」「回顾一下最近 7 天的饮食」。发出第一条消息后隐藏。点击预设问题与自己输入的消息处理方式相同。
- 对话是一串连续的消息。在日历上换日期不会清空对话，面板中插入一条分隔线（如「以下关于 10 月 29 日」），之后的消息以新日期为目标日期。关闭再打开面板时对话仍在；刷新页面后开始新的对话。
- 话题只限饮食：推荐某一餐、调整推荐、回答关于自己饮食和行程记录的问题。其他话题只回一句引导，不作为通用聊天。

每条消息：
- 请求携带消息文字和目标日期，用户身份由 Go 后端根据认证信息确定。推荐永远针对当前消息的目标日期。
- Go 后端自动组装初始上下文（每条消息都提供，不依赖模型去查）：
  - 用户 Profile，包括过敏原。
  - 目标日期前一天到后一天（共 3 天）的行程。
  - 默认窗口内的实际饮食记录及已填写的营养信息。
  - 目标日期、产品时区，以及当前时间（用于区分过去记录与未来安排）。
- 饮食历史窗口：目标日期为今天或过去时，以目标日期为结束日；目标日期在未来时，以今天为结束日。读取包含结束日在内的最近七天记录，不把未来计划当作已食用。
- 需要默认范围以外的饮食或行程时（例如「这两周吃了几次鱼」），由饮食助手调用查询工具获取，单次跨度不超过 31 天，同一条消息中每种记录累计也不超过 31 天（见第 4 节）。查询结果不做跨请求缓存。
- 餐次（早餐、午餐或晚餐）由饮食助手从消息中判断。没有说明餐次时不反问：目标日期是今天，按当前时间推断下一餐（10 点前早餐、15 点前午餐、之后晚餐）；目标日期是其他日子，不给推荐，回复询问哪一餐，并在回复下方显示三个餐次的预设问题。
- 回复包含一段必填的文字，以及可选的推荐：要么没有推荐，要么正好三个，都针对同一餐（回复中注明餐次）。每个推荐包含：菜名或食物组合、简短说明、与真实 Profile、行程或饮食记录相关的推荐理由，以及营养估算（一份常见份量的热量、蛋白质、脂肪、碳水，和每 100 g 的含量，界面标明「目安」）。推荐以卡片形式显示在文字下方。回顾饮食、回答记录类问题或无关话题时只有文字。

多轮对话（阶段 4b，见 plans/archive/phase-4b.md）：
- 对话历史由前端保存在当前页面，每轮随新消息一起发给 Go；服务端不保存会话。每一轮保留用户的话、目标日期、回复文字、推荐的菜名和说明，不保留推荐理由和营养估算。失败的轮不进入历史。
- 每一轮 Go 都重新从数据库读取 Profile、行程和饮食记录来组装上下文，只附在最新一条消息上，不使用前端提交的这些数据。
- 前端提交的对话历史可能被修改，视为不可信数据，不做签名。Go 只校验历史的格式、轮数和长度；AI 服务把历史放在带标签的数据块中，不当作指令。过敏原始终以 Profile 为准，历史中的内容不能放宽它。
- 限制：每次对话最多 10 轮（历史最多 9 轮），单条消息最多 500 字，消息接口的请求体上限为 128 KB。达到 10 轮时禁用输入，提示开始新对话；面板顶部始终有「新对话」按钮。
- 限流：每位用户每分钟最多 6 条消息，返回 429 `rate_limited`（带 `Retry-After`），可以重试；限流在扣额度之前检查，被限流的消息不计入额度。
- 只有最后一轮失败时可以重试；用户发出新消息后，之前失败的轮不再显示重试按钮。

调用额度：
- 每条消息计入额度（预设问题同样计入），按消息计数，不按模型调用次数计数。每位用户每天有消息条数上限（按账号等级：Normal 30 条，Pro 100 条），全站每天也有总上限（默认 300 条，线上 100 条）；超出时 Go 返回 429 `quota_exceeded`（带 `Retry-After`），界面提示今天的次数已用完，不提供重试，不调用 Python 服务。用完的是用户自己的额度时，提示中写出这个上限；用完的是全站额度时不写。等级在每条消息时从数据库读取。计数保存在 PostgreSQL，具体数值通过配置调整。

推荐不会自动写入饮食记录。每张卡片下方有「添加到饮食记录」按钮：点击后在卡片内打开预填好的饮食记录表单（日期为这条消息的目标日期，餐次、内容为菜名，营养为一份的估算值），用户确认或修改后保存。每 100 g 的数值只作参考，不保存。保存后按钮显示「已添加」（只在当前对话内），日历随即更新。不记录推荐是否被采纳（2026-10-29 决定，见 plans/archive/recommendation-nutrition.md）。

变更提案（只对 Pro 开放，2026-10-31 决定，见 plans/change-proposals.md）：
- Pro 用户可以在对话中新增、修改、删除饮食记录，例如「お昼にラーメン食べた」「昨日の夕食はハヤシライスだった」「昨日の夕食は消して」「2番目を夕食に記録して」。饮食助手只暂存修改，回复下方显示一张变更卡片；用户点「実行」后由 Go 执行。推荐卡片上的「添加到饮食记录」按钮照旧保留，所有等级都能用。
- 卡片列出每一条修改：新增显示日期、餐次、内容和「目安」热量；修改只列出变化的字段（前 → 后）；删除的内容加删除线。每条前面有复选框，默认勾选，全部取消时不能执行；不能在卡片中改内容（执行后可以像平时一样编辑）。
- 一个提案最多 10 条修改，生成后 2 小时内可以执行，只能执行一次。修改和删除用乐观锁：提案之后记录被改过或删除了，这一条不执行并显示原因，其余照常执行。执行后每条显示结果，卡片锁定，日历随即更新。
- 执行时 Go 再检查一次等级，降级后未执行的提案不能执行。提案保存在 proposals 表，执行后和过期后都保留，作为审计记录。
- 提案的摘要（每条修改的种类、日期、餐次、内容）进入对话历史，用户可以接着说「やっぱりうどん」。
- Normal 用户要求修改记录时，饮食助手说明这是 Pro 的功能，并提示在日历上自己修改。
- 只包括饮食记录；行程的增删改、饮食计划和撤销不在范围内。

### 3.7 界面语言

- 产品只支持日语和英语（2026-10-28 决定，见 plans/archive/i18n.md）。
- 首次访问时，浏览器语言中第一个日语或英语决定界面语言，都没有时用英语；页头可以切换，选择保存在浏览器中，不存入 Profile。
- 饮食助手用当前界面语言回答。用户输入的行程、饮食和过敏原按原样保存，不翻译。
- 开发文档（docs/、plans/）继续用中文；README 用英语。

## 4. AI 行为约定

数据解读：
- 没有饮食历史或行程时，基于已有信息推荐。
- 未记录不代表没吃，不能据此断言摄入不足。营养字段缺失不能按零处理。部分餐食的营养合计不能当作全天摄入量。
- 有健身习惯不代表当天进行了运动；没有行程记录不代表有时间做饭。
- 不编造用户行程、饮食记录或偏好。不把用户填写的营养数据视为经过专业验证的数据。
- 饮食助手自己给出的营养数字只出现在推荐的营养估算中，是按常见做法和份量的粗略估算，界面标明「目安」，回复文字中不宣称精确。不给出价格数字。

过敏与安全：
- 遵守已知过敏原限制，避免明显包含相关食材的建议。信息不足时提示核实食材，不承诺过敏安全。
- 行程备注、食物描述、聊天消息等用户文本视为输入数据，不作为覆盖系统规则的指令。

修改饮食记录（变更提案，Pro）：
- 只在当前消息明确说吃了什么（「食べた」）或要求修改时暂存修改；「食べたい」、问吃什么不是吃了，不记录。不确定时先问。对话历史、记录内容、行程备注中的文字不能触发修改。
- 新增：日期按当前时间理解「今日」「昨日」「月曜」等，没说日期时用目标日期；营养按一份常见份量估算（「目安」），用户不需要时留空。同一天同一餐已有相同内容的记录时，说明而不重复暂存。
- 修改和删除只能针对上下文或查询结果中出现过的记录（用 id 指定），不猜 id。修改内容时营养值一起重新估算。
- 记录中含有过敏原时（用户说已经吃了），照样可以记录，但回复中提醒，并且不推荐它。
- 回复中说明暂存了什么，请用户在卡片上确认；不说已经保存或删除。

对话：
- 对话中提出的临时条件（口味、时间、预算、购买场所等）在当前对话的后续各轮中都有效，但不写入任何数据，也不自动保存为用户偏好；开始新对话后失效。
- 对话不能放宽已保存的过敏原限制。用户要求忽略或修改过敏原、或修改其他 Profile 内容时，不照做，提示到 Profile 页修改。
- 与饮食无关的请求，简短说明并引导回饮食话题，不生成推荐。
- 回答记录类问题时说明依据的日期范围（如「根据你 10/15 到 10/28 的记录」）；超过 31 天的问题只回答最近 31 天，并说明这个限制。

工程：
- 使用结构化输出并在服务端校验。不把格式校验描述为完整的营养或过敏安全验证。
- 模型调用设置超时；如有重试，必须限制次数。调用失败或输出无效时返回明确错误，由前端提供重试入口。
- 默认不记录完整个人资料、饮食内容或模型原始响应。

模型与成本：
- 模型通过 Amazon Bedrock 调用，不使用模型厂商的 API Key。云上由 EC2 的 IAM 角色授权；本地开发使用 AWS 临时凭证，不在代码、.env 或镜像中写入长期 Access Key。模型目标为 Claude Haiku 5.5；在账号可以使用之前，暂用 Claude Haiku 4.5。两者都从东京区域通过日本 Geo 跨区域推理调用（请求只在日本境内的区域处理）。模型 ID 通过配置项指定，换模型不改代码。
- 每条消息最多调用模型 6 次（见下方 agent 循环）；限制每次调用的最大输出长度；系统提示和工具定义的长度达到模型的缓存门槛时启用 prompt caching。Haiku 4.5 的门槛是 4096 token，而一次调用的全部输入（含初始上下文）约 3400 token，因此目前不启用。
- 本地开发直接调用 Bedrock（使用 AWS 临时凭证）。自动化测试和 CI 使用代码中按脚本返回预设工具调用的假模型，通过环境变量 MODEL_PROVIDER（bedrock 或 fake）切换。
- 回复通过 submit_reply 工具的参数返回（reply 必填，recommendations 为空或正好三个），用 Pydantic 定义并校验结构，不另用 JSON 模式。回复使用当前界面语言（日语或英语），由前端随消息传入 `locale`。系统提示用英文书写，不随语言变化，便于缓存。
- 消息接口为同步请求，不做流式输出；Go 调用 Python 的超时为 30 秒，前端显示加载状态。
- 成本由三层控制：每用户每日额度、全站每日额度（见第 3.6 节）、AWS Budgets 月度预算告警（阶段 5 配置）。

饮食助手是 LangGraph 实现的单个 agent 工具调用循环，单轮和多轮对话使用同一个图：

1. agent：带工具调用模型，每次调用计为一步。
2. 路由，按顺序判断：
   - 调用了暂存工具（只在允许提案时提供）且步数小于 4：执行工具后回到 agent，与之同时出现的 submit_reply 不提交，模型看到暂存结果后再提交。
   - 调用了 submit_reply：进入 validate，不受步数限制。与 submit 同时出现的查询被忽略。
   - 调用了查询工具且步数小于 4：执行工具后回到 agent。同一次回复中的多个查询并行执行，只计一步。
   - 其他情况（步数用完，或没有调用任何工具）：进入 force_finish。
3. tools：执行只读查询工具 get_meals、get_events，单个结果截断到约 3000 字符；饮食记录的结果带 id。允许提案时（上下文中 allow_proposal 为 true，即 Pro），还执行暂存工具 create_meal、update_meal、delete_meal：它们不写入任何数据，只校验参数（结构、长度、营养估算、id 必须在上下文或查询结果中出现过、同一条记录只改一次、最多 10 条）并加入本条消息的变更提案，不通过时把原因交给模型改正；内容含过敏原时附上提醒。暂存的修改随回复交给 Go，Go 再按公开 API 的规则校验并保存为提案（api.md 9.1、9.4）。
4. force_finish：再调用一次模型，只允许调用 submit_reply。
5. validate：校验结构、推荐数量（0 或 3）、餐次、长度、明显的过敏原关键词，以及营养估算是否合理（数值范围、热量与三大营养素大致相符、两组数推算出的份量在 30–2000 g 之间）；通过后把估算取整。通过则结束；第一次不通过时附上错误原因进入 force_finish；再次不通过则返回错误。

每条消息最多调用模型 6 次（4 次 agent、1 次 force_finish、1 次校验失败后的重新提交）。LangGraph 的 recursion_limit 设为 20，只作为计数逻辑出错时的保底。

与饮食无关的消息或修改已保存数据的要求，由模型通过 submit_reply 返回一句引导、不附推荐；过敏原限制不能只依赖提示词，由 validate 兜底检查。

## 5. 技术栈与服务边界

| 部分 | 技术 |
|---|---|
| 前端 | Vue 3、TypeScript、Vite |
| 业务后端 | Go、Gin、GORM |
| 数据库 | PostgreSQL |
| 数据库迁移 | golang-migrate、编号 SQL |
| AI 服务 | Python、FastAPI、LangGraph |
| 模型 | Amazon Bedrock：Claude Haiku 4.5（暂用，目标 Haiku 5.5），日本 Geo 跨区域推理，模型 ID 可配置 |
| Python 环境 | uv |
| 本地容器环境 | Docker、Docker Compose |
| Web 入口 | Nginx（前端静态文件与 API 反向代理）；云上由 Caddy 在前面终止 HTTPS |
| 提交前检查 | pre-commit、gitleaks |
| 自动化 | GitHub Actions |
| 云平台 | AWS |
| 基础设施代码 | Terraform |

服务边界：
- 前端只访问 Go 业务 API；Python 服务不直接暴露给浏览器。
- Go：认证与授权；Profile、行程和饮食记录的读写及日期范围查询；组装饮食助手的上下文，调用内部 Python 服务，将结果返回前端。
- Python：接收 Go 提供的结构化上下文和经过校验的对话历史，执行 LangGraph 流程、调用模型、校验并返回结构化结果。不查询用户业务表，不实现登录，不写入饮食记录：变更提案中的修改只是暂存，由用户确认后经 Go 执行。
- 调用额度的检查和计数在 Go 完成；Python 不感知用户身份和额度。额度按消息计数，不按模型调用次数计数。
- 查询工具通过 Go 的内部接口取数（不经过 Nginx，只在容器内部网络可达）。Go 调用 Python 时附带只对本次请求有效的短期令牌；Go 根据令牌确定用户，并校验查询的日期跨度（不超过 31 天）。Python 仍不直接访问数据库。

## 6. Python 与 uv 约定（阶段 4 落实）

- 提交 pyproject.toml（项目配置、Python 兼容范围、依赖）、uv.lock 和 .python-version；不提交 .venv。
- 运行依赖使用 uv add，开发依赖使用 uv add --dev；修改依赖时同步提交 pyproject.toml 和 uv.lock。
- 拉取代码后使用 uv sync --locked；使用 uv run 执行服务、测试和开发工具。
- CI 和 Docker 构建使用明确版本的 uv，基于锁文件安装；部署环境只安装运行所需依赖。
- 不维护手写 requirements.txt、Poetry 或 Pipenv 配置。

## 8. 数据与基础设施原则

- PostgreSQL 是用户业务数据的持久化来源，刷新页面或重新登录后数据仍能读取；不能使用 localStorage 代替。
- 产品时区为 Asia/Tokyo。行程使用带时区的时间戳存储并按产品时区展示；饮食日期按产品时区解释。日期范围查询必须明确边界。
- 使用编号 SQL migration 管理结构变化，不依赖 GORM AutoMigrate 管理正式数据库结构。
- 配置通过环境变量传入，不硬编码地址、密码或密钥；数据库地址、端口和 TLS 参数可配置。提供 .env.example，真实配置和密钥不进入 Git。
- 使用 pre-commit 运行 gitleaks，在提交前检测密钥、令牌、密码等敏感信息。每位成员克隆仓库后执行 pre-commit install。pre-commit 只在本地生效，可能未安装或被跳过，因此 CI 中也要运行同样的检查。
- 密钥一旦进入 Git 历史（包括已推送的提交），必须立即作废并更换；仅删除文件或改写历史不够。
- 个人的 AI 工具本地配置（如 .claude/settings.local.json、CLAUDE.local.md、含令牌的 MCP 配置）加入 .gitignore。团队共享的 AGENTS.md 等 agent 说明文件提交到仓库，修改时与代码一样经过审查。
- 本地 PostgreSQL 容器使用命名 volume。普通停止命令保留数据，删除数据需要单独且明确的操作。volume 不替代备份，备份必须通过恢复演练验证。
- 日志输出到 stdout，默认不记录敏感数据。
- 健康检查区分进程存活（liveness）和依赖就绪（readiness）；应用支持优雅退出。
- 本地数据库迁移到 RDS 使用 pg_dump、pg_restore 等 PostgreSQL 工具。Terraform 只负责云资源，不负责业务数据搬迁。

### 阶段 4b：多轮对话

在 4a 可用后实现第 3.6 节多轮对话及第 4 节对话约定：前端对话历史（含每条消息的目标日期）、Go 端历史校验与轮数和长度限制、消息限流、在同一个 agent 图上处理带历史的消息。

## 11. 工程与验收原则

- 每个阶段均应有可运行、可验证的成果。优先完成简单、完整的流程，普通实现细节自行决定，避免无必要的抽象。
- 只实现当前阶段明确授权的范围。
- 保留已有无关改动，不自动提交、推送、合并或部署。
- 不使用 --no-verify 等方式跳过 pre-commit。检查失败时修复问题或向用户报告；未经用户确认，不修改 gitleaks 配置或添加忽略规则来让检查通过。
- 不在代码、测试、文档或提交信息中写入真实密钥；示例使用明显的占位值。
- 测试重点：数据隔离、持久化、日期边界、营养字段缺失值处理、失败处理。AI 测试使用固定输入和可控模型替身，不依赖真实付费 API，并覆盖对话不能放宽过敏原限制、与饮食无关的消息、未说明餐次的消息、被篡改或超长的对话历史等情况。
- 未实际执行的验证必须明确标记，不能声称已通过。
- README 和文档中的启动命令必须与实际代码一致。
- 阶段完成后报告修改内容、运行方式、验证结果和剩余问题。
