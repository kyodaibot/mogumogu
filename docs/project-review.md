# Meal App 项目概述

本文件记录长期目标和共同约定，不代表所有功能都应立即实现。具体开发以对应阶段计划（plans/phase-N.md）和用户当前指令为准。

## 1. 项目目标

开发一个以日历为中心的饮食推荐应用。用户在日历中记录行程和实际吃过的食物，系统结合用户 Profile 推荐下一餐。

项目同时用于：
- 学习前端、后端、AI 应用和基础设施开发，建立便于组员共同开发的环境。
- 部署到 AWS，作为可实际访问的全栈作品，展示接口设计、数据管理、自动化检查、云部署和基础运维能力。

## 2. 核心用户流程

日常记录：
1. 注册或登录，首次填写 Profile。
2. 在日历中选择日期，新增、查看、修改或删除当天的行程和饮食记录。

获取推荐：
1. 在日历中选中目标日期（默认今天），点击 Ask AI，选择早餐、午餐或晚餐。
2. 系统自动读取 Profile、相关行程和近期饮食记录，返回三个备选方案（备选，不表示需要全部食用）。
3. 如对结果不满意，可在同一页面用文字追问（如“不想吃辣”“只有 15 分钟”“想在便利店买”），AI 据此更新三个方案。

获取首轮推荐无需输入文字，也无需重复填写已保存的信息。

## 3. MVP 功能

### 3.1 账号与认证

- 注册、登录、退出、获取当前登录用户。
- 用户名与密码登录，密码使用 Argon2id 哈希保存。
- Go 后端签发 JWT，通过 HttpOnly Cookie 保存；校验签名、过期时间、签发者、受众及必要身份字段。
- 退出时清除 Cookie，并在 PostgreSQL 中记录撤销，使旧令牌失效。令牌过期后重新登录。
- 实现基本登录限流、CSRF 防护和适当的 Cookie 配置；生产环境使用 HTTPS。
- 用户数据按用户隔离。所有数据访问依据服务端验证后的身份授权，不信任客户端提交的 user_id。

### 3.2 Profile

支持读取、保存和修改：

| 字段 | 含义 | 类型 |
|---|---|---|
| height_cm | 身高，单位 cm | 数值 |
| weight_kg | 体重，单位 kg | 数值 |
| age | 年龄 | 整数 |
| has_exercise_habit | 是否有健身习惯 | 布尔值 |
| allergens | 过敏原列表 | 字符串数组或 null |
| goal | 目标 | 枚举：build_muscle（增肌）、lose_fat（减脂） |

allergens 的取值含义：
- null：尚未填写。
- []：用户确认无已知过敏原。
- 非空数组：已填写的过敏原。

### 3.3 日历主页面

日历是应用的主要入口。

- 查看并切换月份；默认选中今天，可选择其他日期。
- 在日期中展示行程和饮食记录的摘要；点击日期后展示当天详细记录。
- 在所选日期新增、修改、删除行程和饮食记录。
- 从所选日期发起 Ask AI。

日历组件在阶段 2 选择，满足基本日期展示和点击交互即可。

### 3.4 行程记录

| 字段 | 含义 |
|---|---|
| title | 活动名称（如“上课”） |
| starts_at | 开始日期与时间 |
| ends_at | 结束日期与时间 |
| notes | 可选备注 |

- 同一天允许多条行程。支持新增、按日期范围查看、修改和删除。
- 结束时间必须晚于开始时间；允许跨午夜行程。
- 查询某天的行程时，返回与当天时间范围重叠的行程。
- 每条行程独立存储在 schedule_events 表。

### 3.5 饮食记录

仅记录用户实际吃过的食物。

| 字段 | 含义 | 单位 |
|---|---|---|
| date | 饮食日期 | YYYY-MM-DD |
| meal_type | 早餐、午餐、晚餐或加餐 | — |
| content | 食物名称或描述 | — |
| calories | 热量 | kcal |
| protein_g | 蛋白质 | g |
| fat_g | 脂质 | g |
| carbs_g | 碳水化合物 | g |

- 同一天、同一餐次允许多条记录。支持新增、按日期或日期范围查看、修改和删除。
- 营养字段表示该条记录实际食用份量的总量，不是每 100 克的含量。
- 营养字段可留空：null 表示未知，0 表示用户明确填写为零；数值必须非负。
- 第一版由用户手动填写。

### 3.6 Ask AI 推荐与追问

首轮推荐：

- 请求只携带目标日期和餐次（早餐、午餐或晚餐），用户身份由 Go 后端根据认证信息确定。
- Go 后端自动组装上下文：
  - 用户 Profile。
  - 与目标日期重叠的行程。
  - 近期实际饮食记录及已填写的营养信息。
  - 目标日期、目标餐次、产品时区，以及当前时间（用于区分过去记录与未来安排）。
- 饮食历史窗口：目标日期为今天或过去时，以目标日期为结束日；目标日期在未来时，以今天为结束日。读取包含结束日在内的最近七天记录，不把未来计划当作已食用。
- Python AI 服务返回三个推荐，每个包含：菜名或食物组合、简短说明、与真实 Profile、行程或饮食记录相关的推荐理由。

追问改进：

- 首轮推荐后，用户可在推荐卡片下方输入文字，针对本次推荐提出调整要求。每轮返回一句简短回复和更新后的三个推荐，格式与首轮相同。
- 追问只用于调整本次推荐，不作为通用聊天。
- 对话历史由前端保存在当前页面，每轮随新消息一起发给 Go；服务端不保存会话。刷新页面或更换日期、餐次后，对话重新开始。
- 每一轮 Go 都重新从数据库读取 Profile、行程和饮食记录来组装上下文，不使用前端提交的这些数据。
- 前端提交的对话历史可能被修改，视为不可信数据。Go 校验历史的格式、轮数和长度。
- 限制：每次会话最多 10 轮追问，单条消息最多 500 字，追问请求有限流。

首轮和追问的推荐结果都仅展示在当前页面，不自动写入饮食记录。用户实际吃过后再手动添加。

## 4. AI 行为约定

数据解读：
- 没有饮食历史或行程时，基于已有信息推荐。
- 未记录不代表没吃，不能据此断言摄入不足。营养字段缺失不能按零处理。部分餐食的营养合计不能当作全天摄入量。
- 有健身习惯不代表当天进行了运动；没有行程记录不代表有时间做饭。
- 不编造用户行程、饮食记录或偏好。不把用户填写的营养数据视为经过专业验证的数据。
- 不生成没有依据的精确热量、营养或价格数字。

过敏与安全：
- 遵守已知过敏原限制，避免明显包含相关食材的建议。信息不足时提示核实食材，不承诺过敏安全。
- 行程备注、食物描述、追问消息等用户文本视为输入数据，不作为覆盖系统规则的指令。

追问：
- 追问中提出的临时条件（口味、时间、预算、购买场所等）只在本次会话中生效，不写入任何数据，也不自动保存为用户偏好。
- 追问不能放宽已保存的过敏原限制。用户要求忽略或修改过敏原、或修改其他 Profile 内容时，不照做，提示到 Profile 页修改。
- 与调整本次推荐无关的请求，简短说明并引导回推荐，不生成新推荐。

工程：
- 使用结构化输出并在服务端校验。不把格式校验描述为完整的营养或过敏安全验证。
- 模型调用设置超时；如有重试，必须限制次数。调用失败或输出无效时返回明确错误，由前端提供重试入口。
- 默认不记录完整个人资料、饮食内容或模型原始响应。

LangGraph 工作流是单个 agent 的固定流程：
1. prepare_context：整理和检查上下文及对话历史。
2. classify_message：仅追问时执行。判断消息属于调整推荐、要求修改已保存数据，还是与推荐无关；后两种直接返回引导回复，不进入生成。
3. generate_recommendations：调用 LLM 生成推荐。
4. validate_output：校验结构、数量和明显无效内容；不通过时有限次重试生成，仍失败则返回错误。

## 5. 技术栈与服务边界

| 部分 | 技术 |
|---|---|
| 前端 | Vue 3、TypeScript、Vite |
| 业务后端 | Go、Gin、GORM |
| 数据库 | PostgreSQL |
| 数据库迁移 | golang-migrate、编号 SQL |
| AI 服务 | Python、FastAPI、LangGraph |
| Python 环境 | uv |
| 本地容器环境 | Docker、Docker Compose |
| Web 入口 | Nginx（前端静态文件与 API 反向代理） |
| 提交前检查 | pre-commit、gitleaks |
| 自动化 | GitHub Actions |
| 云平台 | AWS |
| 基础设施代码 | Terraform |

服务边界：
- 前端只访问 Go 业务 API；Python 服务不直接暴露给浏览器。
- Go：认证与授权；Profile、行程和饮食记录的读写及日期范围查询；组装推荐上下文，调用内部 Python 服务，将结果返回前端。
- Python：接收 Go 提供的结构化上下文和经过校验的对话历史，执行 LangGraph 流程、调用模型、校验并返回结构化结果。不查询用户业务表，不实现登录，不写入饮食记录。

## 6. Python 与 uv 约定（阶段 5 落实）

- 提交 pyproject.toml（项目配置、Python 兼容范围、依赖）、uv.lock 和 .python-version；不提交 .venv。
- 运行依赖使用 uv add，开发依赖使用 uv add --dev；修改依赖时同步提交 pyproject.toml 和 uv.lock。
- 拉取代码后使用 uv sync --locked；使用 uv run 执行服务、测试和开发工具。
- CI 和 Docker 构建使用明确版本的 uv，基于锁文件安装；部署环境只安装运行所需依赖。
- 不维护手写 requirements.txt、Poetry 或 Pipenv 配置。

## 7. 页面与数据表

页面：
1. 登录与注册页。
2. Profile 页。
3. 日历主页面：包含 3.3 所列功能、Ask AI 入口、餐次选择、三个推荐卡片和追问输入框。

页面提供必要的加载、空数据、错误和成功状态。

数据表：
- users：账号与密码哈希。
- profiles：用户基础资料，与用户一对一。
- schedule_events：行程记录，与用户一对多。
- meal_records：饮食及营养信息，与用户一对多。
- revoked_tokens：JWT 撤销记录及过期时间。

## 8. 数据与基础设施原则

- PostgreSQL 是用户业务数据的持久化来源，刷新页面或重新登录后数据仍能读取；不能使用 localStorage 代替。
- 产品时区为 Asia/Tokyo。行程使用带时区的时间戳存储并按产品时区展示；饮食日期按产品时区解释。日期范围查询必须明确边界。
- 使用编号 SQL migration 管理结构变化，不依赖 GORM AutoMigrate 管理正式数据库结构。
- 配置通过环境变量传入，不硬编码地址、密码或密钥；数据库地址、端口和 TLS 参数可配置。提供 .env.example，真实配置和密钥不进入 Git。
- 使用 pre-commit 运行 gitleaks，在提交前检测密钥、令牌、密码等敏感信息。每位成员克隆仓库后执行 pre-commit install。pre-commit 只在本地生效，可能未安装或被跳过，因此 CI 中也要运行同样的检查。
- 密钥一旦进入 Git 历史（包括已推送的提交），必须立即作废并更换；仅删除文件或改写历史不够。
- 个人的 AI 工具本地配置（如 .claude/settings.local.json、CLAUDE.local.md、含令牌的 MCP 配置）加入 .gitignore。团队共享的 AGENTS.md 等 agent 说明文件提交到仓库，修改时与代码一样经过审查。
- 本地 PostgreSQL 容器使用命名 volume。普通停止命令保留数据，删除数据需要单独且明确的操作。volume 不替代备份，备份必须通过恢复演练验证。
- 日志输出到 stdout，默认不记录敏感数据。
- 健康检查区分进程存活（liveness）和依赖就绪（readiness）；应用支持优雅退出。
- 本地数据库迁移到 RDS 使用 pg_dump、pg_restore 等 PostgreSQL 工具。Terraform 只负责云资源，不负责业务数据搬迁。

## 9. 分阶段开发

### 阶段 1：最小本地 infra 与前后端骨架（当前阶段）

- PostgreSQL 通过 Docker Compose 运行；Go 和 Vue 在宿主机运行。
- 配置读取、数据库连接、基础日志和优雅退出。
- liveness 与 readiness 接口。
- Vue 开发状态页（后续替换为业务页面）和 Vite API 代理。
- 环境变量示例、启动说明和必要验证。
- .pre-commit-config.yaml（含 gitleaks，固定 hook 版本），README 写明安装步骤（如 uv tool install pre-commit、pre-commit install）。接入时用 gitleaks 扫描一次完整 Git 历史。

暂不实现：账号、日历、业务 CRUD、AI（包括不创建空 Python 项目）、Nginx、完整容器化、CI、云资源。

详细任务与验收标准见 plans/phase-1.md。

### 阶段 2：基础业务与日历

- 数据库迁移。
- 注册、JWT 登录和退出。
- Profile。
- 日历主页面。
- 行程和饮食记录的增删改查。
- 用户数据隔离与前后端联调。

不实现 AI。Ask AI 可显示为尚未开放的入口，不调用不存在的接口，不展示模拟推荐。

### 阶段 3：交付与运维基础

- 前后端 Dockerfile 和完整 Compose 运行方式。
- Nginx 静态文件服务及反向代理。
- GitHub Actions CI，包括对全部文件运行 pre-commit 检查（含 gitleaks）。
- 日志完善。
- 数据库备份与恢复演练。
- 可复现的启动和维护文档。

### 阶段 4：AWS 部署

- EC2 运行应用容器，RDS PostgreSQL 保存业务数据，ECR 保存容器镜像。
- 必要的 VPC、Security Groups 和 IAM 配置；HTTPS 访问。
- Terraform 管理云资源。
- 逐步加入自动部署、CloudWatch、备份和回滚流程。

先运行一套演示环境，接受单台应用服务器的可用性限制。

### 阶段 5a：首轮推荐

实现第 3.6 节首轮推荐及第 4、6 节相关内容：uv 管理的 Python 服务、FastAPI 内部接口、LangGraph 工作流（不含 classify_message）、Ask AI 日期与餐次选择流程、三个推荐方案的展示、失败处理和重试入口。

### 阶段 5b：追问改进

在 5a 可用后实现第 3.6 节追问改进及第 4 节追问约定：追问输入框、前端对话历史、Go 端历史校验与轮数和长度限制、追问限流、classify_message 节点。

## 10. 最终 MVP 暂不包含

- RAG、embedding、向量数据库；菜单库、食谱采集。
- multi-agent、Supervisor、工具循环、checkpoint。
- 通用聊天；服务端保存会话、跨会话的对话记忆；从对话中自动保存用户偏好。
- 图片识别、食物数据库查询、自动营养估算。
- 复杂问卷、目标体重、热量目标及自动营养目标计算；营养图表、周报。
- 第三方日历同步（如 Google Calendar）、重复行程、拖拽排程、日历协作。
- 推荐历史保存；推荐采纳、计划和已食用之间的状态流转；一周菜单和购物清单。
- refresh token。
- Redis、消息队列、Kubernetes；复杂微服务拆分、多环境部署体系、复杂高可用架构。

## 11. 工程与验收原则

- 每个阶段均应有可运行、可验证的成果。优先完成简单、完整的流程，普通实现细节自行决定，避免无必要的抽象。
- 只实现当前阶段明确授权的范围。
- 保留已有无关改动，不自动提交、推送、合并或部署。
- 不使用 --no-verify 等方式跳过 pre-commit。检查失败时修复问题或向用户报告；未经用户确认，不修改 gitleaks 配置或添加忽略规则来让检查通过。
- 不在代码、测试、文档或提交信息中写入真实密钥；示例使用明显的占位值。
- 测试重点：数据隔离、持久化、日期边界、营养字段缺失值处理、失败处理。AI 测试使用固定输入和可控模型替身，不依赖真实付费 API，并覆盖追问不能放宽过敏原限制、与推荐无关的消息、被篡改或超长的对话历史等情况。
- 未实际执行的验证必须明确标记，不能声称已通过。
- README 和文档中的启动命令必须与实际代码一致。
- 阶段完成后报告修改内容、运行方式、验证结果和剩余问题。
