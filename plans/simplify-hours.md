# 尽量回答：营业时间只用常规时间，日期按提问时刻

`plans/cafeteria-menus.md` 和 `plans/menu-stale-fallback.md` 的后续。

现在为了判断「用户提问那一刻食堂开没开」，叠了实时临时休业标记、营业时间 PDF 的人工核对、三种营业状态、按时刻过滤和 `closed`。这些数据源本身不可靠：官网在开门后才更新，导入器 10:30 读到的状态可能是「休息」，并且一整天不再更新。

日期这边，问明天时助手先问「要不要等菜单更新」，用户同意后才参考今天的菜单；用户说的日期和日历不一致时，要求用户去操作日历。

## 已确定（2026-11-24 用户确认）

- **原则**：尽量回答用户的问题，不因为提问的时间不对就不答，或让用户以后再来。助手负责从菜单里选吃什么；当天开不开、几点开，由卡片上的常规营业时间和官网链接告诉用户。
- **接受的代价**：
  - 临时休业（学园祭、节日特别安排）的店也会被推荐；
  - 「14:30 还能吃什么」不再精确排除已关门的店；
  - 题库中考营业时间的评价标准跟着改。
- **问以后的日子**：直接用今天的菜单回答（今天没有菜单时按旧菜单回退的规则用最近的菜单），并告诉用户那天的菜单还没更新。不再先征求同意。
- **相对日期**：「今天」「明天」等按提问时刻（`context.now`，东京时间）计算，不按日历。例如 11/24 提问，「明天」就是 11/25。用户没说日期时才用日历选中的日期。

## 规则

### 营业时间

- 只用官网接口里的**常规时间**（平日、周六、周日、节假日各自的时段）和节假日标记。不读 `tmp_close`，不再核对营业时间 PDF。
- 常规时间只用来做两件事：
  1. 这天这家店不开这一餐的不推荐（如周日不营业的店、只做午餐的店不出现在晚餐里）。`intervals = []` 表示「这类日子通常不营业」。
  2. 卡片显示「通常の営業時間 11:00–14:00」和官网链接。没有记录时只显示官网链接。
- 不再有 `closed` 状态，不再按具体时刻过滤。
- 菜单分类本身的规则保留：早餐套餐只有中央食堂平日供应、「夜」分类只算晚餐、「平日」「土曜日営業」、分类名里写的供应时间。

### 日期

工具查询的是**吃饭的那天**（下称「就餐日」），菜单按下表选取：

| 就餐日 | 用哪天的菜单 |
|---|---|
| 今天以前 | 只用那天的菜单 |
| 今天 | 今天的；某家店没有时，用它前 3 天内最新的 |
| 今天以后 | 那天的菜单已导入就用那天的，否则按「今天」的规则取 |

- 星期、节假日和常规营业时间都按就餐日计算。
- 每家店的 `menu_date` 是实际用的菜单日期，卡片的 `menu_date` 是就餐日。两者不同时：
  - 卡片显示「11/24 のメニューです。11/25 のメニューはまだ更新されていません。」；
  - 回复里没写出菜单日期时，AI 服务在末尾补上同一句。
- 从卡片记录饮食时，记到卡片的就餐日，不是日历选中的日期。

## 验收

1. 导入器单元测试：`tmp_close = 1` 时仍返回常规时段；同时写入今天和明天的记录。
2. 后端集成测试：
   - 常规时间为 `[]` 的店不推荐；没有营业时间记录的店照常推荐；早餐在营业时间未知时可推荐；
   - 就餐日为明天且明天菜单未导入时，返回今天的菜单，卡片 `menu_date` 为明天；
   - 就餐日为过去时只用那天的菜单。
3. `make test`、`make test-integration`、`make test-e2e` 通过。E2E 覆盖：明天的卡片显示统一提示条，记录到明天。
4. `make ai-eval` 的食堂用例通过（含新用例：日历在今天、问明天，工具收到明天的日期）。跑一次 `make quality-eval`，记录新的基线（题库改了，不能与 14:23 的基线直接比较）。
