# 变更提案：在对话中记录、修改、删除饮食记录

> 状态：**已实现，待合并**（2026-10-31）。plans/roadmap-tiers.md 路线图第 3 步，**只对 Pro 开放**。

术语见 GLOSSARY.md（变更提案、饮食记录、账号等级）。

## 目标

用户在聊天面板中用自然语言管理饮食记录，例如：

- 「お昼にラーメン食べた」→ 新增今天午餐的记录（附营养估算）；
- 「昨日の夕食、カレーじゃなくてハヤシライスだった」→ 修改那条记录；
- 「昨日の夕食は消して」→ 删除那条记录。

饮食助手根据需要调用查询和暂存工具，最后显示一张变更卡片，列出每一条修改；用户点「実行」后，由 Go 执行。

## 这个阶段要学会什么

- 怎样让 AI 安全地修改用户数据：AI 只提出修改，用户确认后由服务器校验并执行。
- 乐观锁：数据在「提出」和「执行」之间被改过时，怎样发现并拒绝。
- 审计：记录谁在什么时候提出、确认、执行了什么。

## 已确认的决定（2026-10-31 讨论）

**方式：暂存工具，不直接写入**
- 饮食助手有增删改查四种工具，可以根据需要自由调用：
  - 查：已有的 `get_meals`；
  - 增、改、删：`create_meal`、`update_meal`、`delete_meal`。调用后不写入，只把这条修改加入本次回复的变更提案，并告诉模型「已暂存」。
- 不直接写入的理由：理解错误（「食べたい」被当成「食べた」）、日期算错、删除无法恢复、用户文字中的提示注入、重试导致的重复写入，都会直接变成数据损失。确认只需要多点一次，一张卡片可以确认多条修改。
- AI 服务的令牌保持只读。

**范围**
- 只包括饮食记录的增删改。行程留到下一阶段，按同样的方式加上。
- 不做饮食计划（plans/archive/meal-plan.md 暂缓）和长期记忆。

**等级**
- Go 告诉 AI 服务这次是否允许提案（能力开关，不是等级）。允许时（Pro）才提供暂存工具；Normal 用户要求修改数据时，AI 用文字说明这是 Pro 的功能，并提示可以在日历上自己修改。
- Go 收到提案时和执行时都再检查一次等级；降级后，还没执行的提案不能执行。

**保存与执行**（沿用 plans/archive/meal-plan.md 第 1、2 轮中仍然适用的决定）
- Go 保存提案：新表 `proposals`（id、用户、操作列表、创建时间、执行时间、执行结果）。执行结果记下新建记录的 id，为以后做撤销留好数据。这张表也是审计记录。
- 一个提案只能执行一次。
- 用户在卡片中可以去掉某几条修改，但不能改内容（执行后可以像平时一样编辑）。执行时前端只发「提案 id + 保留的修改的编号」。
- 修改和删除用乐观锁：提案中记下记录当时的更新时间，执行时不一致就拒绝这一条。
- 这一阶段不做撤销。

**校验的分工**（两边都是代码检查，不调用模型）
- Python（质量；不通过就让模型改正）：结构、营养估算是否合理、长度、id 必须见过。过敏原（只对新增和修改后的内容）实施时改为**附提醒、不拒绝**：记录的是用户说已经吃了的东西，拒绝会让它无法记录；提醒让模型在回复中说明，并且不推荐它（2026-10-31 实施时调整）。
- Go（安全和数据；不通过就拒绝）：等级、操作数量上限、记录属于这个用户、字段符合公开 API 的限制（复用饮食记录的校验）、乐观锁。

**对话历史**
- 提案的摘要（每条修改的种类、日期、餐次、内容）放进对话历史，让用户可以接着说「やっぱりラーメンじゃなくてうどん」。

## 已确认的决定（2026-10-31 讨论，第 2 轮）

**指定记录**
- 上下文中的饮食记录和 `get_meals` 的结果都带上 `id`（所有等级；Go 执行时检查记录属于这个用户）。
- `update_meal(meal_id, 要改的字段)`、`delete_meal(meal_id)` 用 id 指定记录。
- 「修改前」的内容由 Go 提供：保存提案时从数据库读取记录的当前内容和更新时间，作为卡片上的「修改前」和乐观锁的依据。Python 只传 id。
- Python 检查暂存的 id 必须是模型在这次对话中见过的（上下文或查询结果中出现过），编造的 id 让模型改正。

**数量与有效期**
- 一个提案最多 10 条修改。
- 提案生成后 **2 小时**内可以执行，超过后返回 `410 proposal_expired`。过期的提案保留在数据库中作为审计记录。
- 不跳过日期已过的记录（补记昨天吃的东西是正常用法）。

**新增**
- 同一餐已有记录时代码不阻止（同一餐可以有多条）。提示词要求先查询；同一天同一餐已有内容相同的记录时，在回复中说明，不重复暂存。
- AI 按一份常见份量估算营养值并写入（复用推荐的营养估算校验），卡片标「目安」；用户说不需要时留空。修改内容时营养值一起重新估算。

**日期**
- 用户说了「今日」「昨日」「月曜」等：以今天为基准计算。没说日期：用目标日期（日历上选中的那天）。

**卡片**
- 新增「＋ 日期 餐次 内容（約 n kcal 目安）」；修改「〜 日期 餐次」，下一行只显示变化的字段（前 → 后）；删除「− 日期 餐次 内容」加删除线。
- 每条前面有复选框，默认勾选；全部取消勾选时「実行」不可点。不做「やめる」按钮。
- 执行后每条显示 ✓ 或 ✗ 加原因（例如提案之后记录被改过）。日历随即刷新，卡片锁定。

**实施**
- 分支 `feat/change-proposals`，4 个里程碑一次完成，中间不等确认，除非遇到需要用户决定的问题：
  1. Go：`proposals` 表；上下文和内部查询接口带 `id`；`allow_proposal`；校验和保存提案（读取修改前的内容）；执行接口（乐观锁、有效期、等级）；历史中的提案摘要；集成测试。
  2. Python：3 个暂存工具；校验（id 必须见过、过敏原、营养估算）；提示词新增一节；假模型能暂存修改；单元测试。
  3. 前端：变更卡片、执行、结果显示、i18n；Vitest、E2E。
  4. 文档与评估：api.md、project-review.md；评估用例（「食べた」要记录、「食べたい」不要记录、修改、删除、日期推断、Normal 用户请求时的回答、用户文字中的提示注入不能触发删除）。

**和推荐卡片按钮的关系**
- 两种方式都保留：推荐卡片上的「食事記録に追加」按钮照旧（打开填好内容的表单，不调用 AI、不用额度、所有等级都能用）；Pro 用户也可以直接说「2番目を夕食に記録して」，由 AI 暂存新增，计 1 次额度。

## 验收标准

1. Pro 用户说「お昼にラーメン食べた」：回复中出现变更卡片（新增、今天、午餐、带「目安」热量）；点「実行」后日历出现这条记录，卡片显示 ✓ 并锁定。
2. 修改和删除：卡片显示修改前后的变化；提案之后在日历上改过这条记录，执行时这一条显示 ✗（记录已被修改），其余照常执行。
3. 同一提案不能执行第二次（409）；超过 2 小时返回 410；降级为 Normal 后不能执行（403）；别人的提案返回 404。
4. Normal 用户要求记录时，AI 不给卡片，用文字说明这是 Pro 的功能，并提示在日历上自己添加。
5. AI 服务的令牌仍然只读；`make test`、`make test-integration`、`make test-e2e` 通过；评估中「食べたい」不产生提案，用户文字中的提示注入不能产生删除。

## 实施结果（2026-10-31）

- 4 个里程碑都已完成：`make test`、`make test-integration`、`make test-e2e`（52 项）通过。
- 评估（`make ai-eval`，真实模型）：19/20。新增的 8 个变更提案用例全部通过（「食べた」、「食べたい」、日期推断、修改、删除、推荐 → 记录、Normal 用户、记录中的提示注入）。唯一失败的是阶段 4b 已知、决定暂不修的「超过 31 天的记录」。
- 实施中发现并修正：
  - Normal 用户说「お昼にラーメン食べた」时，模型曾回答「記録しました」（实际什么都没做）。提示词加了「不能说已经保存、添加、删除」。
  - 新增的提示词一节让「ご飯なしで」的追问有时变成从上一轮中挑一个（新旧提示词各 4 次：旧 4/4，新 2/4）。加了一句「改条件的追问要给 3 个新方案」后 4/4。
- 已知问题：Pro 的回复有时仍写「記録しました。カードの『実行』を押すと記録されます」，前半句不准确；卡片本身写明「実行」前不会保存，暂不处理。
- 成本：Pro 的一次记录或修改要调用模型 2 次，输入约 10,000 token（普通推荐 1 次，约 4,000 token）。系统提示长了约 2,700 个字符（估计约 700 token），所有消息都受影响，每条约多 $0.0007。
