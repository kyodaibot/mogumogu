# 饮食计划：饮食助手一次生成几天的三餐

> 状态：**暂缓**（2026-10-31）。讨论两轮后决定先不做：一次生成一周的计划输出长、等待久、费用高，界面也最复杂，而且「计划了但没吃」会被当成吃过。变更提案的第一个用途改为「在对话中记录饮食」（plans/change-proposals.md）。以后要做饮食计划时，用同样的暂存工具（连续调用 `create_meal`）实现，下面的讨论结果可以参考，但「`submit_reply` 的 `proposal` 字段」已改为暂存工具。

术语见 GLOSSARY.md（饮食记录、饮食计划、计划草案、变更提案）。

## 目标

用户说「来週の献立を作って」之类的话，饮食助手生成接下来几天的三餐，作为**计划草案**显示在聊天面板中。用户删掉不要的几餐后点「全部添加」，这些餐就成为普通的饮食记录，显示在日历上。

## 已确认的决定（2026-10-30 讨论）

**写入方式**
- 间接方式：不做专门的工具。模型在 `submit_reply` 的 `proposal` 字段中输出一组 `create_meal` 操作（见 roadmap-tiers.md），不写入任何数据。AI 服务仍然只有读权限。
- 用户在界面上确认后，由前端把提案发给 Go 的执行接口，Go 校验后写入；模型不参与执行。
- 理由：模型的错误只会停留在草案里；批量写入不可轻易撤销；AI 服务的令牌保持只读，提示注入或重试都不会写入数据。

**饮食记录不增加状态**
- 不区分「计划」和「吃过的」。日期在未来的记录表示打算吃的内容；到了那一天，它就和其他记录一样被当作吃过，没吃的话由用户自己删除或修改。
- 因此不需要数据库迁移，日历和饮食记录表单都不改。
- 代价：日历上分不清「打算吃」和「已经吃了」；用户没删掉的未吃计划，过了那天会被 AI 当作吃过。这和现在推荐卡片上的「添加到饮食记录」按钮一致。

**范围**
- 时间范围由用户在对话中指定，默认从明天开始的 7 天，最多 7 天。
- 只计划早餐、午餐、晚餐三餐，不包括零食，最多 21 餐。
- 已经有饮食记录的那一餐跳过，不覆盖。这一点由代码保证，不依赖模型。
- 只添加：AI 不修改、不删除已有的记录。

**内容**
- 每一餐：菜名和一份的营养估算（复用现有的 `ServingNutrition` 及其校验），没有单独的说明和理由。
- 整个计划：一段总结和推荐理由。
- 生成时考虑目标、过敏原、每天的行程（忙的日子安排快手餐，有聚餐的那一顿不安排），并尽量不重复。
- 不设定每日热量目标的数值。

**触发**
- 模型根据用户的话判断，是普通推荐，还是带 `proposal` 的饮食计划；提示词中有一节说明「先查询已有的安排，再批量生成」。
- 预设问题新增「来週の献立を作って」（英语界面用对应的英文）。

**草案的显示**
- 开头：一行范围说明，例如「11/1〜11/7 の献立案です（3 食 × 7 日、既存の 2 食は除外）」。
- 中间：按天分组，每一餐显示菜名和一份的营养估算；每天显示合计热量（前端相加，标明「目安」）；每一餐可以单独删掉。
- 最后：整体总结和推荐理由，以及「全部添加」按钮。

**AI 能看到未来已有的记录**
- 目标日期在未来时，Go 把那一天已有的饮食记录也放进上下文，标明是「已经安排好的」。AI 可以提到它，也会避免推荐重复的菜。
- 生成计划时，把计划范围内已有的记录告诉 AI，让它避开这几餐，搭配上也不重复。
- 最近 7 天的饮食历史规则不变：仍然以 min(目标日期, 今天) 为结束日。

## 已确认的决定（2026-10-31 讨论，第 1 轮）

**范围**
- 这一阶段只实现一种操作：新增饮食记录（`create_meal`），也就是饮食计划。变更提案的框架（保存、执行接口、审计）一起建好；修改和删除行程、饮食记录，以及长期记忆的 `remember`，以后再加。

**保存与执行**
- Go 保存提案：新表 `proposals`（id、用户、操作列表、创建时间、执行时间、执行结果）。AI 回复时 Go 写入并返回提案 id。
- 用户在草案中只能删掉某几餐，不能改菜名和营养值（添加后可以像平时一样编辑）。执行时前端只发「提案 id + 保留的餐的编号」，Go 只执行这几条。
- 一个提案只能执行一次；执行时 Go 再检查一次等级，降级后不能执行。
- 某一餐已经有记录时跳过，其余照常添加，执行结果中告知跳过了哪几餐，不让整个提案失败。Go 在返回草案之前也先过滤一次，已有记录的餐不显示给用户。
- 同一个对话中可以有多份草案，每份都可以执行；因为会跳过已有记录，重叠的餐不会重复添加。

**输出长度与耗时**
- 模型的输出上限从 1536 提高到 4096 token；Go 调用 AI 服务的超时从 30 秒提高到 60 秒。
- 用 `make ai-eval` 测量生成 7 天计划的耗时和费用；太慢时减少一次最多的天数。
- 生成一次计划先按 1 次额度计算。

**在对话中调整草案**
- 草案的摘要（每一餐的日期、餐次、菜名）放进对话历史。用户说「把周三的晚饭换成鱼」时，AI 生成一份新的完整草案，显示为新的卡片；旧卡片仍可执行。

**Normal 用户**
- Go 告诉 AI 服务这次是否允许提案（`allow_proposal`）。传的是能力开关，不是等级，「等级只在 Go 中判断」不变。
- 允许时 `submit_reply` 的 schema 才有 `proposal` 字段；不允许时，AI 用文字说明饮食计划是 Pro 的功能，可以改为推荐一餐。
- 生成计划的预设问题只对 Pro 显示。

**校验的分工**（两边都是代码检查，不调用模型，不增加 token；只有 Python 校验不通过时，才会让模型重新提交一次）
- Python（质量；不通过就让模型改正）：结构、过敏原、营养估算是否合理、同一份计划中同一餐不重复、菜名和总结的长度。
- Go（安全和数据；不通过就拒绝）：等级、最多 21 餐、日期在今天到 13 天后之间且最多覆盖 7 天、只有早午晚三餐、字段类型和长度符合数据库和公开 API 的限制（尽量复用新增饮食记录的校验）、去掉已有记录的餐。
- 默认范围仍是「从明天开始 7 天」，由提示词决定；「13 天后」是为了让「下周」也在范围内。

## 已确认的决定（2026-10-31 讨论，第 2 轮）

**接口**
- AI 回复的响应新增可选字段 `proposal`：`id`、`summary`、`meals`（每餐的日期、餐次、菜名、一份的营养估算）、`skipped`（Go 在返回前去掉的、已有记录的餐）。
- 执行：`POST /api/proposals/{id}/execute`，请求体 `{"keep": [保留的餐的编号]}`，响应 `{"added": n, "skipped": [...]}`。
- 错误：不存在或属于别的用户 `404 not_found`；已经执行过 `409 proposal_executed`；不是 Pro `403 pro_required`；`keep` 为空或编号无效 `422 validation_failed`。

**撤销**
- 这一阶段不做撤销。`proposals` 的执行结果中记下新建记录的 id，为以后的撤销留好数据。

**草案卡片**（补充上文「草案的显示」）
- 删掉的餐显示为灰色，有「元に戻す」可以恢复（只在执行之前）；全部删掉时「全部添加」不可点。
- 执行后按钮变为「n 食を追加しました」；有跳过的餐时另起一行说明。日历随即刷新，卡片锁定。
- 刷新页面后对话清空，草案也不再显示（和推荐卡片相同）。

**预设问题**
- ja「明日から1週間の献立を作って」，en「Plan my meals for the next 7 days」。用户自己说「来週」时，按下周一到周日计划。

**实施**
- 分支 `feat/meal-plan`，4 个里程碑一次完成（Go → Python → 前端 → 文档与评估），中间不等确认，除非遇到需要用户决定的问题。

## 不在范围内

- 饮食记录的「吃了 / 没吃」状态；
