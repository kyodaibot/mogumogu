# 推荐的营养估算与「添加到饮食记录」

> 状态：**已完成**（2026-10-29），三个里程碑均已实现并通过测试，待合并。在 4b（多轮对话）之前做。分支 `feat/nutrition-estimate`，从 dev 切出。

术语见 GLOSSARY.md（推荐、营养估算）。本计划修改 project-review 第 3.6、4、10 节中「推荐只展示」「不生成营养数字」的约定，修改内容见里程碑 3。

## 已确认的决定（2026-10-29 讨论）

- 每个推荐附带**营养估算**，分两组，都由模型直接给出，彼此不参与计算：
  - **一份**：常见份量的总量（热量、蛋白质、脂肪、碳水）；
  - **每 100 g**：只作参考，让用户自己判断吃多少。组合类推荐（如「饭团加味噌汤」）按整份混合后的平均值给出。
- 卡片显示（ja 与 en 的写法见字典）：
  ```
  約 650 kcal · P 35g F 20g C 80g（目安）
  約 144 kcal / 100g · P 8g F 4g C 18g / 100g（目安）
  ```
- 取整由代码完成，不依赖模型：
  - 一份：热量取整到 10 kcal，三大营养素取整到 1 g；
  - 每 100 g：热量取整到 1 kcal，三大营养素取整到 1 g。
- 回复层面新增 `meal_type`：有推荐时必填，三个推荐都属于这一餐；没有推荐时为 null。
- 卡片下方有「添加到饮食记录」按钮，点击后打开**预填好的** `MealForm`，用户确认后保存：
  - 日期 = 这条消息的目标日期（未来日期也允许）；
  - 餐次 = `meal_type`；
  - 内容 = 菜名；
  - 营养 = 一份的估算值。
  每 100 g 的值不保存，表单也不加克数换算。
- 保存后，这张卡片的按钮变为「已添加 ✓」并禁用（只在当前对话内有效，不持久化），日历重新加载，让餐盘图标立即更新。
- 后端写入沿用现有的 `POST /api/meals`，不增加接口，不改数据表。

## 里程碑 1：AI 服务与 Go

**接口**（`docs/api.md` 第 9 节）

响应中每个推荐新增 `estimate`，回复层面新增 `meal_type`：
```json
{
  "reply": "...",
  "meal_type": "lunch",
  "recommendations": [{
    "name": "...", "description": "...", "reason": "...",
    "estimate": {
      "serving":  {"calories": 650, "protein_g": 35, "fat_g": 20, "carbs_g": 80},
      "per_100g": {"calories": 144, "protein_g": 8,  "fat_g": 4,  "carbs_g": 18}
    }
  }],
  "ask_meal_type": false
}
```

**Python**（`ai/src/mogumogu_ai/`）
- `schemas.py`：
  - 新增 `Nutrition`（4 个字段，都必填、非负）、`Estimate`（`serving`、`per_100g`）；`Recommendation.estimate` 必填；
  - `SubmitReply.meal_type`：`breakfast | lunch | dinner | snack | null`。有推荐时必填，没有推荐时必须为 null；
  - 取值范围：一份的热量 0–10000，其余 0–1000（和饮食记录一致）；每 100 g 的热量 0–900，三大营养素之和 ≤ 100 g。
- `agent.py` 中的 `check_reply`，在现有检查之外再加：
  - 两组数各做一次热量公式检查：`P×4 + C×4 + F×9` 与热量相差在 ±25% 以内（另给 15 kcal 的绝对容差，避免低热量食物因取整误判）；
  - 宽松的一致性检查：`一份的热量 ÷ 每 100 g 的热量 × 100` 在 30–2000 g 之间（每 100 g 热量为 0 时跳过）。
  不通过时沿用现有机制：附上原因，让模型重新提交一次。
- 校验通过后取整，再作为结果返回。
- `prompt.py`：
  - 新增 `# Nutrition estimates` 一节：按常见的一人份估算；组合按整份合计；数值是粗略估算，不要在 `reply` 里宣称精确；
  - 修改原来「不给出没有依据的精确数字」那条：营养数字只能出现在 `estimate` 中；
  - 加入 `meal_type` 的填写规则。
- `tools.py`：`submit_reply` 工具的说明随 schema 一起更新。
- `demo.py`：测试回答里的推荐带上固定的估算值和 `meal_type`。
- 测试（`ai/tests/`）：
  - 现有用例的推荐数据补上 estimate；
  - 新增用例：越界、超出热量公式容差、反推份量不合理时会重新提交；取整结果正确；有推荐但缺少 `meal_type` 时被拒绝。

**Go**
- `internal/assistant/client.go`：`Reply` 新增 `MealType *string`，`Recommendation` 新增 `Estimate`。Go 原样转发，不重复校验。
- `client_test.go` 和 `assistant_integration_test.go`：断言新字段能原样传到前端。

## 实施记录

- `make ai-eval` 7/7 通过（Haiku 4.5）。有推荐的回复输出约 650–970 token，所以模型的最大输出从 1024 提高到 1536。
- eval 发现两处与本功能无关的提示词问题，已一并修复：
  - 用户已说明餐次（如 11:30 问晚餐）时，模型会反问是否要改成午餐。现在明确「按用户说的餐次推荐，不反问」；
  - 超过 31 天的问题，模型有时会查初始上下文之前的那 31 天。现在写明查询范围是「今天减 30 天到今天」。

## 成本

每个推荐多输出 8 个数字，每次有推荐的回复大约多 80–100 个输出 token；输入只多了几行提示。对每日额度和预算没有实质影响。

## 不在范围内

- 食物数据库、营养的精确计算；表单里的克数换算；
- 保存推荐历史，记录推荐是否被采纳，计划与已食用之间的状态流转；
- 多轮对话（4b，另行讨论，上一轮的 Q1–Q8 尚未回答）。
