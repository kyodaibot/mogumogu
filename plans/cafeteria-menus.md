# 京都大学食堂菜单导入与推荐

以下为已确认的第一版范围。

- Digdag 每天日本时间 08:00 开始首轮采集，覆盖三个校区的七家食堂。
- 保存食堂标识。同一道菜可以同时出现在多家食堂的菜单中，每家食堂的菜单条目分别保留。[存储决定](../docs/adr/0003-cafeteria-menu-snapshots-in-postgres.md)
- 注册时必选所属校区（吉田、宇治、桂），校区保存在账号上，之后可在个人资料页修改。引入该字段时，一次性把所有已有账号回填为吉田，包括尚未填写 Profile 的账号。
- 每家食堂记录所在校区。吉田校区采集中央、北部、南部、吉田食堂及カフェテリア・ルネ；宇治校区采集宇治食堂；桂校区采集桂セレネ（650120）。
- Normal 和 Pro 都能使用食堂推荐。用户指定食堂时只在该食堂选；未指定时优先推荐所属校区、用餐时段营业的食堂。推荐要结合常规营业时间，考虑周末、节假日和午晚餐之间的休息时段（2026-11-24 起不再看临时营业公告，见 `plans/simplify-hours.md`）。[吉田营业时间](https://www.s-coop.net/shop_guide/yoshida_shop/) · [宇治营业时间](https://www.s-coop.net/shop_guide/uji_shop/)
- 本校区没有候选时，先询问是否查看其他校区。用户已明确这餐所在校区时，直接按指定校区查找。
- 营业时间固定写在后端代码中（平日、周六；周日休息；祝日按平日），不再读取生协的[公开时间表](https://www.s-coop.net/scms/shophours/getjsonall)（2026-11-24 修改，见 `plans/fixed-hours.md`）。卡片显示该餐次的常规营业时段和官网链接；不判断当天的实际营业状况，也不按具体用餐时刻筛选（2026-11-24 修改，见 `plans/simplify-hours.md`）。
- 七家食堂中，早餐只看吉田校区中央食堂的「朝食プレート」。常规供应时段为授课期间平日 08:00 至 10:00，具体日期以当天安排为准。早餐卡展示当天该分类下的可选款式，按各款官网标示营养值展示。当天没有可用款式时提示早餐暂无可推荐项。[京大生协早餐说明](https://welcome-kyodai.com/start/faq)
- 今天的推荐使用日本时间当天实际采集的官网菜单，排除标为售罄和准备中的菜品，并显示最近一次成功核对官网的时间。采集失败后重试。当天还没成功采集的食堂改用前 3 天内最新的菜单，并标明菜单日期（2026-11-24 修改，见 `plans/menu-stale-fallback.md`）。
- 用户按自己的习惯填写过敏原。每次出卡前，饮食助手逐道对照用户资料原文、相关记忆和该食堂的官方过敏原标记；命中时排除包含该菜的方案，信息不足时说明无法核实。记忆可增加避开的食材，不能放宽资料中登记的过敏限制。
- 用户问明天吃什么时，明天的菜单还没导入就直接用今天的菜单回答，在卡片和回复里标明菜单日期，并说明明天的菜单还没更新。「明天」按提问时刻计算（2026-11-24 修改，见 `plans/simplify-hours.md`）。
- 每张卡是一份方案，可以是一道菜或同一家食堂的多道菜搭配，营养取自食堂标示值。完全相同的搭配只占一张卡，列出能提供整套搭配的所有候选食堂。主菜相同、配菜不同则是不同方案。有足够选择时给三个方案，只有一两个合适方案时按实际数量展示。
- 每家食堂独立发布菜单、独立重试。未指定食堂时，优先从当天已成功更新的食堂中推荐；当天还没有快照的食堂用前 3 天内最新的菜单，卡片和回复标明菜单日期、当天供应未确认（`plans/menu-stale-fallback.md`）。3 天内都没有快照时，告知最近一次成功更新时间；所有食堂都没有可用菜单时，提示菜单尚未取得。
- 分类列表未抓全时重试整家食堂。列表完整但个别详情暂时不可读或格式异常时，先发布已核实的条目，仅补抓失败的详情。官网明确未标热量（如 `-kcal`）的菜跳过，不写入 RDS 菜单条目、不参与推荐；这是已处理的缺值，不触发失败重试。标为 0 kcal 是有效数值。仅其他营养字段缺失时，保留该菜并将对应字段置空。
- 一套搭配默认添加为一条饮食记录。确认前允许移除实际没吃的组成菜，按剩余菜品和份数重新计算营养。
- 日本时间 10:30 按食堂复查一次。完整抓取并校验后，若菜品、价格、供应状态或标示营养值等菜单内容有变化，就更新当天的快照；内容相同则只刷新核对时间。即使当天菜单和昨天相同，当天也算采集成功。复查成功后当天停止抓取。
- 抓取或校验失败时保留当天已有的成功快照。按食堂从上次失败结束算起，依次等待 10 分钟、30 分钟，之后每次等 1 小时，直到本轮成功或日本时间跨日。10:30 若仍在补抓早间菜单，同一家食堂只保留一个采集任务；10:30 起开始的成功采集同时满足午前复查。

## 数据库结构

沿用现有 RDS PostgreSQL。对应迁移 000010 和 000011。

| 表 | 一行表示什么 | 主要字段和约束 |
|---|---|---|
| `users`（已有） | 一个账号 | 新增必填 `campus`，与食堂共用 `yoshida / uji / katsura` 三个合法值。迁移回填吉田，新注册必须显式传值。 |
| `cafeterias` | 一家食堂 | 官网店号为主键，保存名称、校区、菜单入口。 |
| `cafeteria_hours` | 一家食堂在日本当地某日的营业安排 | 店号与营业日期联合唯一。保存来源、核对时间及当天有效的营业时段列表，并标记各餐次的供应时段（如中央食堂早餐 08:00 至 10:00），支持午晚分段。空列表表示这类日子通常不营业，缺少记录表示未知。2026-11-24 起不再使用，营业时间固定在代码中（`plans/fixed-hours.md`）。 |
| `menu_snapshots` | 一家食堂在一天内发布的一版已核实的菜单条目 | 快照 ID、店号、日本采集日期、版本、采集时间、最后成功核对时间、内容摘要。店号、日期、版本联合唯一；读取指定日期的最新成功版本。 |
| `menu_items` | 某版快照里的一道具体规格的菜 | 以快照 ID 和官网菜品编号为联合主键。保存日英名称、分类列表、会员价（日元）、供应状态、详情链接、官网过敏原标记及每份标示营养值。热量必填且非负；蛋白质、脂肪、碳水为可空数值，保留官网精度；盐等其他标示值可按名称和单位保存。 |
| `menu_import_jobs` | 一家食堂某日的一轮导入（早间或午前） | 店号、日期、轮次联合唯一。记录状态、尝试次数、下次重试时间及最近错误，供调度恢复。 |

- 在事务外抓全分类列表并校验详情，再按食堂串行发布已核实的可推荐条目。对规范化后的菜单内容计算摘要（忽略行序，包括分类、供应状态、价格和营养等业务字段）。同日内容相同只更新核对时间；有变化时在一个事务中写入新版本、该版本的所有条目及任务进度。记录待补抓的详情引用，补齐后按同一发布规则更新快照。跨日即使内容相同也建立当天的快照。
- 官网详情链接中的 `t` 标识食堂，`c` 标识菜品规格。跨店用 `c` 比对同一规格；同名不同编号分别保留。同一编号在店内多个分类出现时保留分类归属。若相同编号的门店标示值有差异，卡片使用对应门店的数据。
- 菜品编号按文本原样保存。「朝食プレート」是官网分类，同一天可以列出多个带独立编号的款式。用店号和分类识别早餐候选，保留各款的编号、供应状态和营养值。
- Go 按目标日期、用餐时段和校区读取候选。卡片可列的食堂是整套搭配各菜可选食堂的交集。每个营养字段单独求和，有任一组成菜缺该字段时，套餐该字段标为未知。用户确认添加时将所选方案的份量营养复制到现有 `meal_records`，以后菜单改价或改配方都不改写个人记录。

## 应用分工与验收

- **离线导入**：将实验爬虫整理为可按食堂独立运行的 importer，负责解析官网分类、菜品详情和营业安排，规范化后发布快照。Digdag 调度首次采集、午前复查和到期补抓，任务状态以导入任务表为准。importer 使用仅有菜单表权限的数据库角色，用户请求无需等待官网。
- **Go 菜单模块**：向助手提供两个操作。查询候选时接受目标日期、餐次、预计时间和可选的指定食堂，结合账号校区、营业和供应状态，返回带快照引用和官网过敏原标记的菜品或具体无结果原因。生成卡片时只接受本次查询返回的菜品引用与份数，检查整套搭配可供应的门店，合计该店标示值并附出处。多个食堂标示值不同时保留门店差异。营业安排无法确认时明确提示，过敏原资料不全时保留未知状态。
- **Python 饮食助手**：沿用现有对话流程，通过 Go 内部接口查候选，结合口味、日程和既往饮食选择方案并说明理由。食堂模式的模型输出为菜品引用、份数和理由，最终价格、营养、可选食堂和来源由 Go 填充。菜单链接来自已导入的详情页，Normal 和 Pro 都可使用，独立于现有 Pro 网络搜索权限。
- **前端与契约**：从聊天面板拆出食堂推荐卡，用结构化字段展示门店、适用时段、标示营养值与最后核对时间。早餐的一张卡包含可选款式，添加到日历前确定实际款式、门店和份数。旧版估算卡与新卡通过显式类型区分，兼容已有标签页中的会话。先扩展历史校验及跨层契约，再启用 0–3 张新卡。
- **交付顺序**：先完成校区迁移和单店离线导入，以中央食堂早餐贯通官网详情、RDS、助手卡片和饮食记录；再扩至七店、跨店搭配和营业例外；最后接上正式调度并演练部分失败、跨日和服务重启。固定网页样本验证解析，数据库集成测试验证发布与筛选，用共享契约和端到端用例验证一张早餐卡、两张晚餐卡及旧对话续用。
