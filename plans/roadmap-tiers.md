# 路线图：账号等级、变更提案与长期记忆

> 状态：**方向已确认**（2026-10-30）。这是几个阶段的总体框架，不直接授权实施；每个阶段开始前另写详细计划（plans/phase-*.md 或单独的计划文件），由用户确认。

术语见 GLOSSARY.md（账号等级、变更提案、饮食计划、计划草案、饮食记录）。

## 目标

- 账号分为 **Normal** 和 **Pro** 两个等级。Pro 可以使用更多的调用额度，可以让饮食助手修改数据（经用户确认），并且有长期记忆。
- 短期的对话记忆（多轮对话，4b）作为基础功能，所有用户都可以用。
- 饮食助手始终**没有写权限**：所有对数据的修改，都以变更提案的形式交给用户确认，再由 Go 执行。

## 已确认的决定（2026-10-30 讨论）

**账号等级**
- 由管理员授予（`make` 命令或脚本），不做支付功能。
- 等级只在 Go 中判断。Go 根据等级决定每次请求的额度、是否允许提案、是否附带长期记忆；不依赖提示词。

| 功能 | Normal | Pro |
|---|---|---|
| 单轮推荐、营养估算 | ✅ | ✅ |
| 多轮对话（4b） | ✅ | ✅ |
| 每日额度 | 30 | 100 |
| 变更提案（饮食计划，修改或删除行程和饮食记录） | ❌ | ✅ |
| 长期记忆 | ❌ | ✅ |

- 全站每日上限保持 100。饮食计划等较长的回复先按 1 次计算，上线后根据实际费用再调整。
- 从 Pro 降级为 Normal：
  - 长期记忆保留，但不再用于推荐；用户仍然可以查看和删除；重新升级后恢复使用；
  - 还没执行的提案作废：执行时 Go 会再检查一次等级。

**工具与变更提案**
- 饮食助手的工具只有两类：
  - **查询工具**（`get_meals`、`get_events` 等）：结果返回给模型，所有等级都可以用；
  - **提交**（`submit_reply`）：交出最终的回答。
- `submit_reply` 新增可选字段 `proposal`，是一个操作列表，例如 `create_meal`、`update_event`、`delete_meal`、`remember`。只有当 Go 允许时（Pro），schema 中才出现这个字段；Go 收到后还会再检查一次。
- 不做专门的「饮食计划工具」：饮食计划就是只包含 `create_meal` 的提案，由提示词引导「先查询已有的安排，再批量生成」。
- 执行由用户触发，不是模型触发：用户在变更提案卡片上点「実行」，前端把提案发给 Go，由 Go 执行。模型不参与执行这一步，所以用户确认的内容就是实际执行的内容。
- 安全措施（对所有提案都一样，和等级无关）：
  - AI 服务的令牌始终只读，并且限定用户、短期有效；
  - 执行时 Go 再做一次完整校验，规则和公开 API 相同（字段、所属用户、等级）；
  - 修改和删除带上数据的更新时间，执行时发现不一致就拒绝（乐观锁），提示用户重新生成；
  - 一个提案只能执行一次；
  - 每个提案的操作数量有上限；
  - 审计日志：提案内容、提出时间、确认时间、执行结果。

**长期记忆（Pro）**
- 分工：Python 决定「记什么」，以 `remember` 提案的形式提出；Go 负责保存、权限，以及查看、修改、删除记忆的页面。
- 存在 Go 管理的 `memories` 表里（golang-migrate），每次请求全部放进上下文，不使用向量检索。
- 只有用户确认后才保存。对话中的临时条件（「今天不想吃辣」）不应该成为长期记忆。
- 不使用 LangGraph Store 和 LangMem：它们要求 Python 直接连接数据库，并且默认由模型直接写入记忆，这与上面的分工和「确认后保存」都冲突。以后如果需要语义检索，再考虑 pgvector（Python 计算 embedding，Go 存储和检索），或者一个基于 Go API 的自定义 Store。

## 路线图

1. **4b：多轮对话**（所有用户）。设计问题见之前提出的 4b-Q1〜Q8，开始前讨论。对话历史要能容纳提案（例如计划草案中每一餐的日期、餐次、菜名），这样之后可以说「把周三换成鱼」。
2. **账号等级**：`users` 表加等级字段、按等级的额度、管理员授予的命令、界面上显示等级。
3. **变更提案**：`proposal` 字段、提案卡片（显示修改前后的内容）、Go 的执行接口和审计日志。第一个用途是饮食计划（plans/meal-plan.md），之后扩展到修改和删除行程、饮食记录。
4. **长期记忆**（Pro）：`remember` 提案、`memories` 表、记忆管理页面、放进上下文。

## 待定（在对应阶段的计划中讨论）

- 每个提案的操作数量上限，修改前后的显示方式，提案中的数据在执行前被用户修改时怎样提示。
- 记忆的条数和长度上限；怎样防止被诱导保存的记忆成为长期的提示注入（例如记忆内容的校验、在上下文中标明它是用户数据而不是指令）。
- 饮食计划的输出长度上限（现在是 1536 token）和耗时。
- 管理员命令的形式（只在服务器上通过 SSM 执行，还是本机通过 API 执行）。

## 不在范围内

- 支付和订阅；
- 跨对话的自动记忆（不经用户确认）；
- 向量数据库、LangGraph Store、LangMem；
- 饮食记录的「吃了 / 没吃」状态；购物清单。
